## 2. Review by area

### 2.1 HTML rendering (remote sender → viewer) — defence in depth
1. **ammonia allow-list** (`sanitize.rs`): scripts, forms/inputs, iframes, objects, event handlers and `javascript:` URLs removed; link schemes limited to http/https/mailto; relative URLs denied; `rel="noopener noreferrer nofollow"` added. `<img src>` kept **only** for raster `data:image/{png,jpeg,gif,webp}` (no SVG, no `srcset`). Remote images are removed and counted ("N remote images blocked") unless the user loads them (2.7).
   **CSS (v0.2):** `<style>` blocks and `style`/`class`/`bgcolor`/`align`/… attributes are kept so newsletters render properly, but every declaration goes through `sanitize_css`: `expression()`, `-moz-binding`, `behavior`, `javascript:`, `@import` and `</style` breakouts are dropped; `url()` keeps only inline raster `data:` images, remote URLs become `none` (or the fetched data URL when the user loaded images). The iframe CSP (point 2) is the backstop if a CSS trick slipped through: no network fetch is possible from the message document.
   **cid: images** are resolved from the message's own MIME parts and inlined as `data:` URLs, raster types only (png/jpeg/gif/webp, no SVG).
2. **Per-message CSP** injected into the iframe document: `default-src 'none'; img-src data:; style-src 'unsafe-inline'; font-src 'none'; form-action 'none'; base-uri 'none'`, so even a sanitizer bypass could not fetch remote resources (tracking) or load fonts.
3. **Sandboxed iframe** `sandbox=""` (no scripts, opaque origin, no forms/popups/top navigation) with `srcdoc` and `referrerpolicy="no-referrer"`; it cannot reach the Tauri IPC bridge.
4. Search snippets use U+0002/U+0003 markers rendered as Svelte text nodes, never `{@html}` (the UI contains no `{@html}` at all).

Verified: 11 sanitizer tests (incl. safe CSS kept, dangerous CSS dropped, remote `url()` substitution, `</style>` breakout) (script/iframe/form/on*/javascript:/tracker/srcset/scheme-relative/SVG data) plus the GUI ("Phishing test" and "tracking pixel" fixtures, screenshots 02, 03 and 09).

### 2.2 App CSP and Tauri capabilities (least privilege)
- `tauri.conf.json` CSP: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; frame-src 'self' http: https: mailto:; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. `freezePrototype: true`, `withGlobalTauri: false`.
  - **Why `frame-src` lists http/https/mailto (v0.2):** without it, WebKit blocks a link click inside the message iframe *before* the navigation policy runs, so links could never reach the confirm dialog (found in GUI testing). Allowing these schemes in `frame-src` only lets the navigation *request* reach the Rust handler, which **cancels every navigation** that is not the app itself (2.9). Nothing is ever loaded into the frame; `connect-src`/`img-src` still allow no remote origin.
- Commands are declared in an **app manifest** (`build.rs`, 21 commands), so each needs an explicit `allow-*` permission. `capabilities/main.json` grants the `main` window those 21 commands, `core:event:allow-listen`/`allow-unlisten`, and **one plugin permission: `opener:allow-open-url` scoped to `http://*` and `https://*`**. No `core:default`; **no** fs, shell, http, dialog or `opener:allow-open-path` permission for the webview. Opening attachments and showing file dialogs happen in Rust commands (2.8), so a compromised UI cannot open arbitrary paths or show a picker to exfiltrate files.

### 2.3 Credential storage
- Passwords live in the Secret Service (GNOME Keyring) via `keyring` 3 (`sync-secret-service`, `crypto-rust`), service `dev.neutronmail.NeutronMail`, key `account-<id>`. They are never in SQLite or config. Checked: `grep testpass` on the db, WAL and the logs returned 0 matches.
- Fallback when no Secret Service: **memory only** for the session (never plaintext on disk), shown in the UI as "⚠ no keyring".
- An account is persisted only **after** a successful IMAP login. If storing the password fails, the account row is rolled back.
- Verified in the GUI: backend=Keyring, and after an app restart, background sync ran without a credential error.

### 2.4 TLS
- rustls 0.23 (ring) with certificates **always** validated. Roots are the Mozilla bundle (`webpki-roots`) plus an optional user-supplied private CA (adds trust, never disables it). There is no "accept invalid certificates" switch anywhere.
- STARTTLS is **mandatory** when selected (IMAP: `STARTTLS` must return OK; SMTP: `Tls::Required`). There is no plaintext fallback, and no plaintext mode exists.
- Tests: an untrusted certificate is rejected for IMAP and SMTP; both STARTTLS and implicit TLS work against the private CA.

### 2.5 Logging
- `tracing` only. Logs contain account ids, folder names, counts and error texts. They never contain passwords, message bodies or addresses. `tracing-log` is not enabled, so `log` records from async-imap/lettre (protocol traces) are never emitted.
- New tests assert that IMAP and SMTP authentication errors do not contain the password (`format!("{err} {err:?}")`).

### 2.6 Local data — encrypted cache (v0.3)
- The mail cache (`cache.sqlite3` + `-wal`/`-shm`: account settings, folders, raw RFC 822 messages, FTS index, address history, trusted image senders) is encrypted with **SQLCipher** (rusqlite `bundled-sqlcipher`, AES-256-CBC + HMAC-SHA512 per page, linked against the distribution's libcrypto so OpenSSL security updates apply).
- **Key:** 256 random bits from the OS RNG (`getrandom`), used as a raw SQLCipher key (`x'…'`, no passphrase KDF needed). Stored in the Secret Service (GNOME Keyring) as `dev.neutronmail.NeutronMail` / `cache-key`, next to the account passwords; read back after creation so data is never encrypted with a key the keyring did not keep. In memory it lives in `Zeroizing` buffers; `Debug` never prints it; it is never logged.
- **Migration:** at startup a file starting with the plain `SQLite format 3` header is encrypted in place: WAL checkpoint → `sqlcipher_export` into `cache.sqlite3.encrypting` → `PRAGMA integrity_check` with the key → atomic rename → the old file, WAL and SHM are **overwritten with zeros, fsynced and deleted**. Tested (`tests/encrypted_cache.rs`) and in the GUI on the real profile: the account and 26 messages survived; afterwards no file in the data dir contains a known plaintext string or the SQLite header.
- **No keyring** (or keyring error): the cache is an **in-memory database** for the session, like the password fallback. Nothing is written to disk and existing files are not touched; the UI shows "⚠ cache in memory". (GUI-tested in a D-Bus session without gnome-keyring: 0 cache files created.)
- **Key lost** (keyring reset) while an encrypted cache exists: the unreadable file is moved aside (`cache.sqlite3.unreadable-<time>`, not deleted) and a fresh cache is created; the user is told that accounts must be added again.
- Files remain mode 0600 in a 0700 directory.
- Limits: the key is as safe as the login keyring (unlocked while you're logged in, so malware running as you can read both); overwriting the old plaintext is best effort on SSDs / copy-on-write filesystems (btrfs is Fedora's default), so full-disk encryption is still recommended. WebKit's own storage (localStorage for the theme) is not encrypted and holds no mail.

### 2.7 Remote images (opt-in, fetched by the core)
- Blocked by default. "Load remote images" (per message) or "Always load from this sender" (per sender, stored in `image_senders`, revocable with "Stop loading …") makes the **Rust core** fetch them; the webview never touches the network, so the CSP stays `img-src data:`.
- `remote.rs` (reqwest 0.12 + rustls): http/https only; max 3 redirects; 5 s connect / 10 s total timeout; no cookies; generic User-Agent, no Referer.
- **SSRF guard:** a custom DNS resolver refuses loopback, private, link-local, CGNAT, multicast, unspecified, documentation and IPv6 ULA/link-local addresses (and IPv4-mapped forms); IP-literal URLs and every redirect target are checked too. A mail therefore cannot make the client probe the LAN or `localhost` services. (Debug builds honour `NEUTRON_ALLOW_PRIVATE_IMAGE_HOSTS=1` so the local test server can be used; release builds ignore it.)
- Limits: 5 MB per image, 25 MB and 40 images per message, 6 parallel fetches. The body is **magic-byte sniffed** (PNG/JPEG/GIF/WebP only), so an HTML or SVG "image" is rejected (fixture `fake.png`: rejected and reported as "could not be loaded").
- Privacy note (by design): loading remote images tells the sender's server your IP and that you opened the mail. That is why it is opt-in.

### 2.8 Attachments
- **Received:** file names are sanitized (`safe_filename`): basename only (`../../.bashrc` → `bashrc`), control and bidi-override characters removed (RLO trick `report\u202Etxt.exe` → `reporttxt.exe`), leading dots stripped, Windows reserved names prefixed, max 120 chars keeping the extension. `is_risky` flags executables/scripts by extension, MIME type and magic bytes (ELF, MZ, `#!`); risky files are marked in red and **Open** requires a second confirmation.
- **Save** uses the native GTK save dialog driven from Rust (`blocking_save_file`), prefilled with the safe name; the user chooses the location. **Open** writes a private copy (0600 in a fresh 0700 directory under the app cache) and hands it to the default application via the opener plugin from Rust. Copies are deleted on the next app start.
- **Outgoing:** the picker is also Rust-side (`blocking_pick_files`); the UI only receives **opaque tokens** + name/size, never paths, and can't attach a file the user did not pick. Limits: 25 MB per file and per message, 50 attachments; oversize files are rejected with a message. Messages are built with `mail-builder` (multipart/mixed); CR/LF in subject or addresses is rejected (header injection).
- **Forward** carries the original attachments (re-read from the cached raw message by index), byte-for-byte (integration test + GUI test compare bytes).

### 2.9 Links
- The iframe stays `sandbox=""` (no scripts). wry/WebKitGTK reports subframe navigations to Tauri's `on_navigation`, so a link click in a message is intercepted in Rust **and always cancelled**; only `about:blank`/`about:srcdoc` and the app origin are allowed (the dev server origin only in debug builds). The main window is created in `setup` so the handler is attached before any content loads.
- The link is analysed in Rust (`links.rs`) and sent to the UI: only **http, https and mailto** are accepted (other schemes produce a "Blocked link" notice). The confirm dialog shows the **real host** (IDN as punycode, so look-alike domains are visible), the cleaned URL, and the original URL. Hover shows the actual target in a status pill (WebKit `mouse-target-changed`), not the link text.
- Tracking cleanup: LinkedIn `/comm/` paths and tracking parameters, `linkedin.com/redir/redirect?url=` and similar `?url=`/`?u=` redirectors are unwrapped (the dialog says so); `utm_*`-style parameters are stripped. "Open original" is still available. `lnkd.in` short links can't be resolved offline and are shown as-is.
- mailto opens the in-app composer (to/cc/bcc/subject/body prefilled); nothing leaves the app until the user presses Send.

### 2.10 Sending, replies, drafts
- Reply uses Reply-To/From; Reply all adds To+Cc minus your own address (deduplicated). `In-Reply-To` = parent Message-ID, `References` = parent References + parent Message-ID; Forward sets only References. Verified on the server in the GUI.
- **Bcc** recipients go only into the SMTP envelope; the sent message has no Bcc header (verified on the server: `X-Test-Envelope-To` lists the Bcc address, headers don't). Drafts *do* keep a Bcc header so they can be resumed — they are stored in your own Drafts folder.
- Drafts are APPENDed with `\Draft \Seen`; saving again or sending replaces/deletes the old draft (UID EXPUNGE). A failure to delete is reported.
- **Sent copy:** if the copy to Sent fails, the UI shows "Sent, but the copy could not be saved to Sent: …" (GUI-verified by making the server's Sent folder read-only).

### 2.11 Contacts (evolution-data-server)
- Read via D-Bus (`zbus` 5, pure Rust, no libebook C bindings): `Sources5` to list enabled address books, `AddressBook10.OpenAddressBook` + `GetContactList` with an `x-evolution-any-field` "contains" query. The query string is escaped for EDS's S-expression syntax (`sexp_escape`, tested). Calls have a 4 s timeout; if EDS isn't running the composer silently falls back to addresses from your own mail cache ("Recent", ranked below contacts) and retries EDS after 60 s.
- Contact data is only read (the seeding example in `crates/neutron-core/examples/eds_seed.rs` is for tests). Suggestions are cached in memory for 30 s; nothing about contacts is logged except counts.

### 2.12 HTML composing (v0.3)
- The editor is a `contenteditable` element **in the app page** (not sandboxed), so everything that enters it is sanitized by a stricter **compose policy** (`sanitize_compose_html`): no `<style>` blocks, no `class`/`id` (app CSS can't be targeted or spoofed), an allow-list of CSS properties without `position`, `z-index`, `transform`, `top/left`, `background-image` or any `url()` (quoted mail can't draw over the app UI), images only as inline raster `data:` URLs (remote images dropped, never fetched), links only http/https/mailto with `rel="noopener noreferrer nofollow"`.
- Applied (1) to the quoted original for Reply/Reply all/Forward and to resumed drafts, in Rust; (2) to every paste and drop (`text/html` goes through the `sanitize_compose_html` command; files are refused); (3) **again before sending/saving**, authoritatively, so a compromised UI can't send unsanitized HTML. The editor also has `contain: paint` as a CSS backstop, and the app CSP blocks inline script and remote images.
- Links are added through an in-app link bar that accepts only https/http/mailto (`javascript:` is refused; GUI-tested).
- Sent as `multipart/alternative` (text + HTML); inline images become `multipart/related` parts referenced by `cid:` (identical images share a part). The **text/plain part is generated in Rust from the sanitized HTML** (quotes as `> `, lists, link URLs), not taken from the UI, so both parts always match. Max 20 MB of HTML.
- Sender names/dates in the quote header are HTML-escaped (test with `Eve <script>`); a plain-text original is escaped and quoted with `<br>`.
- Users can switch a message to **plain text** (formatting dropped) per message.
- Tests: 6 in `tests/compose_html.rs` (sanitizer policy incl. `position:fixed`, hostile paste, multipart structure and cid matching, quoting, text alternative) + the reply-all integration test now checks the delivered `multipart/alternative` with the quote. GUI: reply to the HTML newsletter with bold/list/paste, forward saved as a draft and resumed with formatting, new mail with a link; MIME tree and content verified in the server's Maildir.
- Limits: `document.execCommand` (deprecated but supported by WebKitGTK) drives the formatting; WebKit may add `style` (e.g. `rgb()` colours, `font-size: medium`) on paste, which the allow-list keeps. Class-based styling of quoted newsletters is dropped (layout may be simpler than the original).

### 2.13 Account settings (v0.3)
- **Editing an account** (`update_account`) validates the config and **logs in to the (possibly new) IMAP server before saving anything**; a wrong password or a server/TLS error leaves the stored account and keyring entry untouched (GUI-tested: "Login failed … Nothing was saved."). An empty password keeps the keyring entry; the password is never sent back to the UI. The IDLE watcher is stopped and restarted with the new settings. Certificate verification can't be turned off here either (only a private CA can be added).
- **Signature** is stored per account, sanitized with the compose policy (2.12) on save (no script, handlers, remote images; max 256 KB), and inserted in Rust (`compose::with_signature`) between the cursor and the quote with the RFC 3676 `-- ` delimiter, which is kept in the generated text/plain part. Not re-inserted when a draft is resumed.
- **Sync window** (allow-listed values: all, 30, 90, 365, 730 days): new mail is fetched only from `UID SEARCH SINCE`, and cached messages older than the window (minus one day of slack for the server's date granularity) are **deleted from the local cache only**; the server is never modified (integration test checks the server still has both messages; GUI-tested with a 2020 message: skipped, downloaded with "All mail", pruned again with 30 days, still in the server Maildir). Unread counts reflect the cached window.
- **Trusted image senders** are listed per account and can be removed; removal takes effect on the next open (GUI-tested: images blocked again, no new request in the image-server log).
- **Remove account** needs an in-app confirmation, stops the watcher, deletes the keyring password, and deletes the account row; folders, messages, settings and the trust list go with it (`ON DELETE CASCADE`, test re-adds an account and finds no leftover settings or trusted senders). Mail on the server is not touched.
- New commands (`update_account`, `get/set_account_settings`, `list_image_senders`, `new_draft`) are added to the least-privilege capability explicitly.
- Tests: 5 in `tests/account_settings.rs` (settings round-trip + sanitizing, rejected values/unknown account/oversize, update + cascade, signature placement and `-- ` in the text part, sync window against Dovecot).

### 2.14 Incremental sync (v0.4)
- Per folder the cache stores UIDVALIDITY, UIDNEXT, EXISTS, HIGHESTMODSEQ and the sync window used. A changed UIDVALIDITY drops the cached folder and its state; a changed sync window, a missing UIDNEXT or a cache from before v0.4 forces one full pass (`UID SEARCH ALL`/`SINCE` diffed with the cache).
- Incremental: new mail via `UID SEARCH UID <UIDNEXT>:*` (filtered, since `n:*` always matches the highest UID); expunges are detected by arithmetic (`EXISTS == old EXISTS + new UIDs` ⇒ none), otherwise one `UID SEARCH ALL` finds the vanished UIDs. Flags: with CONDSTORE (`SELECT … (CONDSTORE)`) only `FETCH 1:* (FLAGS) (CHANGEDSINCE m)`, nothing if HIGHESTMODSEQ is unchanged; without CONDSTORE all flags are refetched (fallback, tested by forcing it off). The new state is written only after the folder sync succeeded, so an interrupted sync is repeated from the old state.
- The 500-new-messages cap is gone: new mail is downloaded newest first in pages of 500 (FETCH chunks of 50), each page committed in one SQLite transaction. The message list pages too (200 rows per scroll page), and the count line shows the folder total.
- **Every IMAP command now has a 60 s timeout** (`imap::cmd`, including streaming the response; IDLE keeps its own wait), connect/login keep their 20 s limit. Fixes O13.
- Tests: `tests/sync_large.rs` (5,000 messages; sizes via `NM_LARGE_N`) and `tests/imap_timeout.rs` (a TLS server that accepts LOGIN and then never answers: `SELECT` fails with `Timeout` after the 2 s test timeout). Debug build, local Dovecot 2.4, this box:

  | Step | 5,000 msgs | 10,000 msgs |
  |---|---|---|
  | First full sync (download + parse + FTS index, encrypted-store code path but plaintext test DB) | 1.25–1.31 s | 3.05 s |
  | No-change incremental sync | 9–12 ms | 17 ms |
  | 10 new + 3 flag changes (CHANGEDSINCE returns 13 rows, not n) | 16 ms | 27 ms |
  | 5 expunges (one UID SEARCH ALL) | 22 ms | – |
  | Full sync without CONDSTORE | 0.95 s | – |
  | Incremental without CONDSTORE (all n flags refetched) | 119 ms | – |
- GUI: a 3,000-message folder synced completely (the old code would have stopped at 500); 200 expunged and 10 marked read by another client were reflected after one refresh (unread 1000 → 930, matching the server), and scrolling loads past the first page ([screenshot](screenshots/sync-large-folder.png)).
- Not done: QRESYNC/VANISHED (expunges still need one UID SEARCH ALL when they happen), and folders are still synced one after another on one connection.

### 2.15 GNOME Calendar and invitations (v0.4)
- **Agenda:** `EdsCalendar` lists `[Calendar]` sources from the EDS registry (enabled and selected only), opens each via `CalendarFactory.OpenCalendar` and queries `(occur-in-time-range? (make-time …) (make-time …))` with `GetObjectList`. Read-only; the D-Bus connection stays open; 4 s timeout per call; retried at most once a minute; without EDS the strip is hidden. Recurring events are expanded by Neutron (FREQ DAILY/WEEKLY/MONTHLY/YEARLY, INTERVAL, COUNT, UNTIL, BYDAY for weekly; detached RECURRENCE-ID instances replace the series instance; CANCELLED events skipped).
- **Invitations:** the first `text/calendar`/`application/ics` part (≤ 512 KB) is parsed by a small Rust iCalendar reader (`ical.rs`: unfolding, quoted params, text unescaping, TZID through the IANA database incl. libical's `/freeassociation.sourceforge.net/…` prefix, VTIMEZONE standard offset as a fallback, floating/all-day, DURATION; field lengths and event counts capped). The card is rendered from structured data as Svelte text nodes (no HTML from the invite).
- **REPLY** (RFC 5546/6047): built in Rust with only UID, SEQUENCE, DTSTAMP, RECURRENCE-ID, DTSTART/DTEND (UTC), SUMMARY, ORGANIZER and the user's own ATTENDEE line; text is escaped, `CN` params quoted and stripped of quotes/controls, addresses validated (no `:`/`;`/`"`/whitespace), PARTSTAT from an allow-list, lines folded at 75 octets on UTF-8 boundaries. A unit test checks CRLF injection in SUMMARY can't add properties. Sent as `multipart/alternative` (text + `text/calendar; method=REPLY`) to the organizer only, `In-Reply-To` the invitation; a copy goes to Sent. Only `METHOD:REQUEST` from an organizer other than the user can be answered.
- **Add to calendar** (default on, not for Decline): a fresh VEVENT (UTC times, RRULE copied, the user's PARTSTAT, STATUS TENTATIVE/CONFIRMED) is written with `CreateObjects`, or `ModifyObjects` when the UID already exists (an updated invitation). The answer is recorded per message (`invite_responses`, encrypted cache, deleted with the message).
- **Least privilege:** 3 new commands (`upcoming_events`, `get_invite`, `respond_invite`) granted explicitly; the webview gets no D-Bus access.
- Tests: 6 unit (`ical`: invite parsing incl. TZ/VTIMEZONE/folding/VALARM, REPLY shape + injection, calendar round trip, durations/dates, recurrence, size cap), `tests/invite.rs` (invite in the cache → REPLY over the local SMTP server; delivered message checked for envelope, In-Reply-To, `method=REPLY` and PARTSTAT), `tests/eds_calendar.rs` (real EDS in a private session: 4 seeded events incl. a daily series and a past event, query order, update by UID, Neutron-built event accepted; plus EDS-absent → error without a hang).
- GUI (EDS in the app's D-Bus session, demo events from `examples/seed_calendar.rs`, invite from `testserver/seed_invite.py`): the agenda showed the seeded events; Accept sent the REPLY (checked in the Maildir: To/envelope the organizer, `METHOD:REPLY`, `PARTSTAT=ACCEPTED`), the card switched to "You accepted · in your calendar", and after an app restart the event appeared in the agenda from EDS.
- Not done: `METHOD:CANCEL` only shows a "Cancelled event" card (the event is not removed from the calendar automatically); counter-proposals/delegation; recurrence rules beyond the subset above (BYMONTHDAY, BYSETPOS, EXDATE…); writing to calendars other than Personal; DST-exact recurrence (series are stepped in UTC). Invitations from Exchange using Windows TZIDs without a VTIMEZONE fall back to local time.

### 2.16 Unread badge and new-mail notifications (v0.4)
- **Badge:** the inbox unread count goes into the window title (`Neutron Mail (73)`, GUI-verified) and is sent as a `com.canonical.Unity.LauncherEntry` `Update` signal (count + count-visible) for docks that support it (Dash to Dock / Ubuntu Dock; stock GNOME Shell ignores it, untested on a real dock). One new command, `set_unread_badge` (count clamped), granted explicitly.
- **Notifications:** after a background (IDLE/poll) sync, unread INBOX mail with a UID above the pre-sync maximum triggers one `org.freedesktop.Notifications.Notify` (one sender + subject, or "N new messages" with the first three); later ones replace the same bubble (`replaces_id`). Not on an account's first sync (empty cache), not while the window has focus, nothing for other folders. Sender/subject are stripped of control characters, capped at 300 chars and markup-escaped (`&`, `<`, `>`; unit-tested) because GNOME Shell interprets a markup subset in the body. Notification bodies contain sender and subject only, never message text.
- GUI: with another window focused, two messages appended over IMAP produced "2 new messages" in the session's notification daemon (dunst on the box, not GNOME Shell) with `<3 &` shown literally ([screenshot](screenshots/notification-and-badge.png)). No per-account on/off switch yet.

### 2.17 Provider profiles, autoconfig and OAuth2 (v0.5)
- **Profiles** are static data with official sources (README table); unit tests check host names, port/security pairs and domain detection (no suffix tricks: `gmail.com.evil.test` is not Google).
- **Autoconfig fetch:** only the domain (never the full address) goes into the URL; HTTPS only (`https_only`, no HTTP fallback, ≤3 redirects, still HTTPS), 8 s timeout, 64 KB streamed cap, DTD/ENTITY documents rejected, host names validated, `plain` socket types dropped (SSL preferred over STARTTLS). The result only pre-fills the form; the user sees it and nothing connects until "Add account" (with full certificate verification as before). Residual risk: a hostile domain's own autoconfig server can suggest a different (TLS-verified) server, which is inherent to autoconfig and visible in the form. The lookup reveals the domain to Mozilla's ISPDB (`autoconfig.thunderbird.net`).
- **OAuth2:** authorization-code flow with PKCE S256 (RFC 7636 test vector), 256-bit `state` checked on the loopback request (requests with a wrong state are ignored), loopback listener bound to `127.0.0.1` on an ephemeral port, one request at a time with a 5 s read timeout and a 5 min overall timeout. Token endpoints must be HTTPS (plain HTTP only for loopback, used by the mock-server tests); no redirects followed. Client IDs/secrets are never in the repo (env at build or run time). Errors show the provider's `error`/`error_description` but never tokens; `Tokens`' Debug output hides them.
- **Token storage:** the JSON token set replaces the password in the same Secret Service item (or the in-memory fallback). Refreshes are serialized by a mutex so concurrent syncs can't race on a rotated refresh token. Removing the account deletes the item. Refresh tokens are long-lived credentials with the full mail scope; they are as sensitive as the password was.
- New commands `list_providers`, `detect_provider`, `autoconfig_lookup`, `oauth_sign_in`, `oauth_configured`, granted explicitly. `add_account`/`set_password` refuse OAuth accounts; changing an account's sign-in method requires a new sign-in.

### 2.18 Folders, moving mail and rules (v0.6)
- **Folder names:** names are validated before anything is sent (no control characters, `*`/`%`, the hierarchy delimiter, empty path parts or a new `INBOX`); non-ASCII names go out as modified UTF-7 (RFC 3501 §5.1.3, round-trip tested) unless the server enabled `UTF8=ACCEPT`. Mailbox names are always sent as quoted strings by async-imap. Special-use folders (RFC 6154) and INBOX cannot be renamed, moved, deleted or unsubscribed, enforced in the Rust core (the UI only greys the items out).
- **Delete** works deepest-first, moves messages to Trash first unless the user chose permanent deletion in the confirmation, and the cache rows go only after the server succeeded.
- **Move/copy:** `UID MOVE` (RFC 6851) when advertised, otherwise `UID COPY` + `\Deleted` + `UID EXPUNGE` (UIDPLUS) or `EXPUNGE`; both paths are integration-tested (the fallback by forcing it). Batches of 200 UIDs. The cache is updated immediately and the folders are re-synced in the background. Undo finds the moved messages again by Message-ID (newest UID), so messages without a Message-ID are counted as `untracked` and can't be undone (shown in the count). The `undo_transfer` command checks that the target folder belongs to the transfer's account.
- **Rules model and limits:** ≤200 rules, ≤20 conditions and ≤10 actions each, patterns ≤500 characters, regexes compiled with the linear-time `regex` crate under a 256 KB program / 2 MB DFA limit (a catastrophic-backtracking pattern like `(a+)+$` on 100 KB is tested to finish quickly), and at most 256 KB of body is scanned. Rules are validated on save (backend), including keywords (IMAP atom rules) and forward addresses, and stored as JSON in the SQLCipher cache.
- **Loops and storms:** rules only run on messages that are new in INBOX during an incremental sync, never on the first download; each message is claimed once (`rule_runs`, by Message-ID or UIDVALIDITY/UID), so a moved message can't trigger again. Move/copy into INBOX or into the message's own folder is rejected. Forwards are skipped for mail with `Auto-Submitted` (≠ `no`), `X-Neutron-Rule`, or from the account's own address; forwards carry `Auto-Submitted: auto-forwarded` (RFC 3834) and the original as `message/rfc822`; ≤3 forwards per rule and a budget of 20 forwards per account per hour. Tested end to end: the forwarded copy comes back through SMTP/LMTP, matches the rule again, and is not forwarded again. Adding a forward target in the UI requires an explicit confirmation.
- **Sieve / ManageSieve:** the client requires STARTTLS (RFC 5804) with the same certificate verification as IMAP, discards nothing silently (bytes received before the TLS handshake abort the connection), re-reads capabilities after TLS, authenticates only with SASL PLAIN inside TLS, caps lines (64 KB) and literals (1 MB), and times out after 20 s. Scripts are checked (`CHECKSCRIPT`) before `PUTSCRIPT`/`SETACTIVE`. Generated Sieve escapes `"`/`\` in strings and `*`/`?` in `:matches`, only exports regexes from a portable subset, and keeps a rule local (with the reason shown) when it can't be expressed. While our script is active, server-side rules are not also run locally. Tested against Dovecot Pigeonhole: upload, activation and filing of a message delivered over SMTP→LMTP.
- New commands `create_folder`, `rename_folder`, `delete_folder`, `set_folder_subscribed`, `move_messages`, `undo_transfer`, `list_rules`, `save_rules`, `test_rule`, `run_rules_now`, `sieve_status`, `sieve_upload`, `sieve_disable`, each granted explicitly in the capability file. `test_rule` never changes or sends anything.

### 2.19 Notes and To-do (v0.7)
- **Storage:** notes, note folders, tags, task lists, tasks and email links live in the same SQLCipher cache as mail (new tables, migrated at start-up). Every note and task has a random UUID v4 `uid`, `modified` time, `sync_state`, `remote_ref` and `etag` columns, and deletes leave a tombstone, so IMAP-notes or CalDAV VTODO sync can be added later without a schema change. Priorities use iCalendar values (1 high, 5 medium, 9 low, 0 none) and are validated in the core. No data leaves the machine.
- **Note HTML:** the editor is a `contenteditable`; pasted content is sanitized in the frontend, and **every save is sanitized again in Rust** with ammonia: an allow-list of formatting tags, `href` only with http/https/mailto, only `data-checklist`/`data-checked` attributes, no images, styles, classes, event handlers or scripts (unit-tested with `<script>`, `onclick`, `<img>`, `style` and `javascript:` payloads). Clicks on links in notes are subject to the same Rust-side navigation guard as the rest of the app.
- **Email links** store the Message-ID, subject, sender and date, not the message body. "Open email" resolves the Message-ID against the local cache for that account only; if the message is no longer cached, a notice says so.
- **Search** uses parameterized `LIKE` with `%`, `_` and `\` escaped (tested).
- **Reminders:** a background task checks every 20 s, marks each reminder as fired *before* notifying (no repeats after a crash), and shows a desktop notification plus an in-app toast. Verified in the GUI.
- 24 new commands (`list_notes`, `save_note`, `note_from_message`, `list_tasks`, `save_task`, `set_task_completed`, …), each granted explicitly in the capability file. Subtasks are one level deep; completing a parent completes its subtasks.

## 4. Not covered / limits of this audit
- No fuzzing of mail-parser/ammonia, and no third-party penetration test.
- WebKitGTK sandboxing and the bubblewrap/Flatpak setup were not evaluated.
- Fedora 44: build + RPM install checked in a `fedora:44` container (see README); the app itself was not run on a Fedora GNOME desktop.
- GNOME Calendar was tested against evolution-data-server 3.56 in a private D-Bus session, not against GNOME Calendar's UI or online (Google/CalDAV) calendars.
- CSS-only phishing tricks (layout spoofing) are not prevented beyond what the CSP blocks (see O10).
- The opener/xdg-open handoff was tested with Chrome and MuPDF in an isolated XDG session on the box, not on a real GNOME desktop.
